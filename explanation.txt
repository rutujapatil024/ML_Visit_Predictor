================================================================================
                     "SHOULD I VISIT?" CROWD PREDICTOR
                      Complete Project Documentation
================================================================================

This document provides a comprehensive explanation of the architecture, data pipeline,
machine learning models, backend logic, and frontend design of the "Should I Visit?" 
tourist recommendation application.

--------------------------------------------------------------------------------
1. PROJECT OVERVIEW & OBJECTIVE
--------------------------------------------------------------------------------
"Should I Visit?" is a machine learning-based web application designed to help tourists 
decide the best time to visit famous Indian landmarks. Based on a user-selected date and 
destination, the system predicts:
  * Crowd levels (Low, Moderate, High, Extreme)
  * Predicted crowd count (actual visitor numbers via regression)
  * Average daily temperature (C)
  * Weather conditions (Sunny, Clear, Rainy, Cloudy) — live forecast or ML prediction
  * Landmark-specific peak season details
  * Indian holidays and festivals on that day

Using these metrics, the system calculates a proprietary "Visit Score" (0-100) and
returns a recommendation of YES, MAYBE, or NO, alongside customized travel tips,
top 3 alternative dates in the next 60 days, and interactive crowd trend charts.

--------------------------------------------------------------------------------
2. DATASET DETAILS (data.xlsx)
--------------------------------------------------------------------------------
The project utilizes historical observations in "data.xlsx":
  * Total Rows: 730 daily observations
  * Time Period: 2 years (2024 - 2025)
  * Destinations: 8 famous Indian landmarks
    1. Taj Mahal, Agra
    2. Red Fort, Delhi
    3. India Gate, Delhi
    4. Qutub Minar, Delhi
    5. Varanasi Ghats, Varanasi
    6. Gateway of India, Mumbai
    7. Mecca Masjid, Hyderabad
    8. Sanchi Stupa, Madhya Pradesh
  * Core Columns:
    - Date (YYYY-MM-DD)
    - Time (dropped during cleaning)
    - Place (Landmark name)
    - Crowd_Count (in Thousands)
    - Weather (Sunny, Clear, Rainy, Cloudy)
    - Day_of_Week (Monday to Sunday)
    - Holiday (Yes / No)
    - Event (Regular Day, Festival, National Holiday, Cultural Event)
    - Temperature (C)
    - Week_of_Year (0 to 52)
    - Special_Features
    - Region & Transportation_Type

--------------------------------------------------------------------------------
3. DATA CLEANING & PREPROCESSING (train_model.py)
--------------------------------------------------------------------------------
Before training the machine learning models, the following steps are performed:
  1. Date Parsing: The 'Date' column is converted to pandas datetime format.
  2. Time Dropping: The 'Time' column is removed since visit forecasts are calculated
     on a daily granularity.
  3. Handling Missing Values: Null values in 'Special_Features' are replaced with 'None'.
     Rows with missing critical values are dropped.
  4. Duplicate Removal: Rows with duplicate 'Date' + 'Place' combinations are removed
     to prevent data leakage and train-set distortion.
  5. Feature Encoding: LabelEncoder is used to encode categorical text variables:
     - 'Place' is mapped to classes 0 through 7.
     - 'Weather' is mapped to classes 0 through 3.
     - 'Event' is mapped to classes 0 through 3.
     - 'Day_of_Week' is mapped to classes 0 through 6.
     - 'crowd_level' (the target classification label) is mapped to classes 0 through 3.
     All encoders are saved in 'models/encoders.pkl' for use during live inference.

--------------------------------------------------------------------------------
4. FEATURE ENGINEERING
--------------------------------------------------------------------------------
To capture seasonality and calendar factors, the following features are generated:
  * month: Extracted from the Date (1 - 12) to model monthly temperature & peak crowd trends.
  * day_of_month: Extracted from the Date (1 - 31).
  * Week_of_Year: Extracted from the Date (0 - 53) to capture high-resolution season changes.
  * is_weekend: Binary flag (1 if Day_of_Week is Saturday or Sunday, else 0).
  * is_holiday: Binary flag (1 if Holiday is "Yes", else 0).
  * is_festival: Binary flag (1 if Event is "Festival", "National Holiday", or "Cultural Event", else 0).
  * crowd_level (Target Label): Created by categorizing the raw 'Crowd_Count (in Thousands)' 
    using domain-specific thresholds:
      - Low: <= 9,999 visitors
      - Moderate: 10,000 to 21,999 visitors
      - High: 22,000 to 34,999 visitors
      - Extreme: >= 35,000 visitors

--------------------------------------------------------------------------------
5. MACHINE LEARNING MODELS & MULTI-MODEL ENSEMBLE
--------------------------------------------------------------------------------
The project implements a Multi-Model Ensemble setup for both classification (Crowd Level) 
and regression (Crowd Count). In addition, it employs a Random Forest Regressor for 
temperature prediction, and a statistical weather lookup table fallback.

A. Crowd Level Classifiers (Low, Moderate, High, Extreme)
Three classifier models are trained and compared side-by-side:
  1. Random Forest Classifier:
     * Algorithm: RandomForestClassifier (n_estimators=100, max_depth=10, random_state=42)
     * Performance: ~66.4% test split accuracy.
     * Role: Primary model. Excellent generalization and handles features without scaling.
  2. Decision Tree Classifier:
     * Algorithm: DecisionTreeClassifier (max_depth=10, random_state=42)
     * Performance: ~68.5% test split accuracy.
     * Role: Alternative model, offering high interpretability and local split accuracy.
  3. Gradient Boosting Classifier:
     * Algorithm: GradientBoostingClassifier (n_estimators=50, max_depth=5, random_state=42)
     * Performance: ~68.5% test split accuracy.
     * Role: Alternative model, utilizing boosting to correct sequential errors.

Feature Importances (as calculated by Gini Importance from the primary RF Classifier):
  1. place_enc (~31.2%): The landmark itself is the strongest crowd predictor.
  2. event_enc (~17.8%): Special events/festivals strongly dictate crowd size.
  3. day_of_month (~17.7%): Monthly cycle fluctuations.
  4. Week_of_Year (~14.4%): High resolution seasonal trend indicators.
  5. month (~8.7%): Broader seasonal variations.
  6. is_festival (~4.5%): Overlap festival flag.
  7. is_weekend (~4.0%): Weekend leisure travel patterns.
  8. is_holiday (~1.6%): National/local holiday overlap.

B. Crowd Count Regressors (Granular predicted visitor numbers)
Three regressor models are trained and compared side-by-side:
  1. Random Forest Regressor:
     * Algorithm: RandomForestRegressor (n_estimators=150, max_depth=12, random_state=42)
     * Performance: MAE of ~2,750 visitors, R² Score ~0.76.
     * Role: Primary regressor. High accuracy for mapping complex seasonal shapes.
  2. Decision Tree Regressor:
     * Algorithm: DecisionTreeRegressor (max_depth=12, random_state=42)
     * Performance: MAE of ~3,656 visitors, R² Score ~0.61.
     * Role: Alternative regressor.
  3. Gradient Boosting Regressor:
     * Algorithm: GradientBoostingRegressor (n_estimators=50, max_depth=5, random_state=42)
     * Performance: MAE of ~2,918 visitors, R² Score ~0.74.
     * Role: Alternative regressor.

C. Temperature Predictor (RandomForestRegressor)
  * Target: Average daily temperature in C (Continuous variable)
  * Algorithm: RandomForestRegressor (n_estimators=100, random_state=42)
  * Why Selected: Captures geographical temperature dynamics across northern vs. southern India.
  * Performance: Mean Absolute Error (MAE) of ~4.8C.

D. Weather Forecast Lookup (Historical Mode Table)
  * Target: Weather category ('Sunny', 'Clear', 'Rainy', 'Cloudy')
  * Implementation: A statistical mode (most frequent) lookup table keyed by (Place, Month).
  * Note: Used as a fallback for predictions beyond 16 days. For dates within 16 days, 
    the system queries the live Open-Meteo API.


--------------------------------------------------------------------------------
6. APP PREDICTION & RECOMMENDATION ENGINE (app.py)
--------------------------------------------------------------------------------
When a user queries a landmark and date, the backend performs the following steps:

1. Feature Extraction: Parses the queried date to compute day_of_month, month, is_weekend,
   week_of_year, event_type, is_festival, and is_holiday.
2. Holiday/Festival Enrichment: Fetches holidays DYNAMICALLY from the Python 'holidays'
   library + Nager.Date API. Data is cached per-year in memory. This replaces the old
   hardcoded INDIAN_HOLIDAYS dictionary and works for ANY future year automatically.
3. ML Execution: Calls the saved Random Forest models to predict:
   - Crowd Level (classification)
   - Crowd Count (regression — actual predicted visitor numbers)
   - Temperature (regression)
4. Confirmed Visitor Blending (NEW):
   - Queries the SQLite database for confirmed visitors for this place + date.
   - Blends ML prediction with real-time confirmed data using the formula:
     final_count = (ML_WEIGHT * ml_count) + ((1 - ML_WEIGHT) * confirmed_count * SCALE)
   - ML_WEIGHT = 0.6 (60% ML, 40% live confirmed data)
   - CONFIRMED_VISITOR_SCALE = 50 (each confirmed user represents ~50 actual visitors)
   - The blended count is always at least the estimated real visitors.
5. Weather Resolution:
   - For dates within 16 days: Fetches LIVE weather from Open-Meteo API (see Section 9).
   - For dates beyond 16 days: Falls back to ML weather lookup table.
   - Response includes a "weather_source" field indicating "Live Forecast" or "ML Prediction".
6. Visit Score Calculation (0 - 100):
   * Base Score: Determined by the predicted crowd level:
     - Low: 90
     - Moderate: 65
     - High: 38
     - Extreme: 15
   * Weather Penalty:
     - Rainy: -12 (slippery roads, poor outdoors experience)
     - Sunny: -5 (harsh sun)
     - Cloudy: -3 (moderate visibility)
     - Clear: 0 (optimal)
   * Temperature Penalty:
     - Temp > 38C: -12 (risk of heatstroke/dehydration)
     - Temp > 36C: -8 (heavy discomfort)
     - Temp <= 36C: 0
   * Natural Jitter: A deterministic pseudo-random hash noise of -5 to +5 is added based 
     on the date string to reflect real-world natural fluctuation on adjacent dates.
   * Clamped: The final score is bound between 0 and 100.
7. Recommendation Categories:
   * YES: Visit Score >= 70
   * MAYBE: Visit Score between 40 and 69
   * NO: Visit Score < 40
8. Better Dates Scan:
   * Backend automatically runs the prediction pipeline for the next 60 days.
   * Returns the top 3 dates with the highest overall Visit Score.
9. Contextual Travel Tips:
   * Extreme Heat warning (Temp >= 38C): limit exposure, carry hydration.
   * Rain (Rainy): Bring umbrellas, caution on slippery stone steps.
   * Crowds (High/Extreme): Book tickets online to avoid queue, arrive before 8:00 AM.
   * Low Crowds: Enjoy a peaceful, relaxed visit.

7. FLASK WEB APPLICATION STRUCTURE
--------------------------------------------------------------------------------
The frontend dashboard is designed as a single-page web app using Flask:
  * Backend API:
    - GET '/' : Renders the home template with landmark selections.
    - POST '/predict' : Accepts JSON {place, date, session_id} and returns crowd
      prediction, score, temperature, weather, tips, holiday details, confirmed
      visitors data, blended predictions, and better dates.
    - POST '/compare' : Accepts JSON {places, date} (2 or 3 landmarks) and returns
      a comparative breakdown, flagging the absolute best destination with an "is_best" key.
    - POST '/chart-data' : Accepts JSON {place, date} and returns monthly crowd trend
      data for Chart.js visualization (dates, crowd counts, temperatures, levels).
    - POST '/confirm-visit' : Accepts JSON {place, date, session_id} and stores a
      confirmed visit in the SQLite database. Returns updated confirmed count.
    - POST '/cancel-visit' : Accepts JSON {place, date, session_id} and removes a
      confirmed visit. Returns updated confirmed count.
    - POST '/live-stats' : Accepts JSON {date, place?} and returns real-time confirmed
      visitor counts for one or all places on that date.
    - POST '/holidays' : Accepts JSON {year} and returns dynamically fetched holiday
      data for the requested year from the holidays library + Nager.Date API.
  * UI/UX Aesthetics:
    - Dark-mode primary design with glassmorphism panels.
    - Split-screen results layout presenting a high-resolution landmark image banner 
      alongside the color-coded recommendation verdict card.
    - Horizontal side-by-side Multi-Model Ensemble cards displaying predictions and metrics in parallel.
    - Visual landmark comparison cards featuring postcard-quality thumbnail images with hover scale zoom effects.
    - Vibrantly color-coded badges matching recommendation states (Green for YES, Orange for MAYBE, Red for NO).
    - Circular SVG progress indicators showing the Visit Score.
    - Interactive Chart.js bar/line chart showing monthly crowd trends with temperature overlay.
    - Weather source badge indicating "Live Forecast" or "ML Prediction".
    - Confirmed visitor counter with live pulsing green dot indicator.
    - "I'm Planning to Visit" confirmation button with toggle between confirm/cancel states.
    - Prediction source breakdown bar showing ML vs confirmed data blend.
    - Highly responsive layout adapting gracefully to mobile (collapsing to vertical columns) and desktop.
    - Integrated Landmark Comparison Drawer to contrast weather, temperature, and crowds.

8. WEATHER API INTEGRATION (Open-Meteo)
--------------------------------------------------------------------------------
The application integrates live weather forecasts from the Open-Meteo API:

  * API: Open-Meteo (https://open-meteo.com/) — Free, no API key required
  * Coverage: 16-day weather forecasts for any global coordinate

  * Implementation:
    - Each landmark has stored GPS coordinates (latitude, longitude)
    - For dates within 16 days from today: Live API call fetches real forecast data
    - For dates beyond 16 days: Falls back to ML weather lookup + temperature model
    - API returns: daily max/min temperature, WMO weather code

  * WMO Weather Code Mapping:
    - Codes 0-1: Clear
    - Codes 2-3, 45-48, 71-77, 85-86: Cloudy
    - Codes 51-67, 80-82, 95-99: Rainy
    - Temperature is computed as average of daily max and min

  * Error Handling: If API call fails (timeout, network error), gracefully falls back
    to ML prediction without disrupting the user experience.

  * User Indicator: A badge ("Live Forecast" or "ML Prediction") is shown in the
    weather section so users know the data source.

9. INTERACTIVE ANALYSIS CHARTS (Chart.js)
--------------------------------------------------------------------------------
The application includes interactive monthly crowd trend and hourly density curves:

A. Monthly Trends Chart
  * Technology: Chart.js v4.4.4 (CDN-loaded)
  * Data: Generated by the '/chart-data' backend endpoint
  * Chart Type: Combined bar + line chart
    - Bars: Predicted crowd count per day, color-coded by crowd level
      (Green=Low, Yellow=Moderate, Orange=High, Red=Extreme)
    - Line: Temperature overlay on secondary Y-axis (orange color)
    - Selected date is highlighted with a gold border on its bar
  * Interactivity: Hover tooltips showing date, crowd level, visitor count, temperature, and score.

B. Hourly Distribution Curves
  * Data: Generated dynamically in the `/predict` endpoint using landmark-specific
    operating hours and peak/off-peak density weights.
  * Hourly Intervals: 6:00 AM, 8:00 AM, 10:00 AM, 12:00 PM, 2:00 PM, 4:00 PM, 6:00 PM, 8:00 PM.
  * Chart Type: Line chart with filled area underneath
    - Area Line: Expected crowd density (visitor distribution count)
    - Line: Expected hourly temperature variation (coolest mornings, peak mid-afternoon heat)
  * Optimal Visit Time: Calculates the single hour matching the lowest relative crowd count 
    and coolest temperature window (e.g. 6:00 AM or 8:00 AM for outdoor monuments).

10. LIVE CALENDAR INTEGRATION
--------------------------------------------------------------------------------
The application fetches Indian holidays and festivals dynamically using two sources:

  * Primary: Python 'holidays' library (v0.40+)
    - Supports India (country code 'IN') with government holidays.
    - Automatically calculates dates for any year (no hardcoding needed).
    - Works offline without API keys.

  * Supplementary: Nager.Date API (free, no key required)
    - URL: https://date.nager.at/api/v3/PublicHolidays/{year}/IN
    - Fetches additional public holidays not covered by the library.
    - Falls back gracefully if the API is unavailable.

  * Holiday Classification:
    - Each fetched holiday is classified into: National Holiday, Festival,
      Religious Holiday, Regional Holiday, or Public Holiday.
    - Classification uses keyword matching against the holiday name.

  * Caching:
    - Holiday data is cached in-memory per year on first access.
    - Pre-warms cache for current year and next year at app startup.
    - Festival season windows (approximate busy-period ranges) remain as static
      data since they represent general patterns, not exact dates.

--------------------------------------------------------------------------------
11. CONFIRMED VISITOR TRACKING SYSTEM
--------------------------------------------------------------------------------
The application includes a real-time confirmed visitor system:

  * Storage: SQLite database (visitors.db)
    - Table: confirmed_visits (id, place, date, session_id, created_at)
    - Unique constraint on (place, date, session_id) prevents duplicates.
    - Auto-created on first app startup.

  * Session Management:
    - Each browser gets a persistent session ID stored in localStorage.
    - Format: 'sess_{timestamp}_{random}'
    - Ensures one confirmation per user per place-date.

  * Blending Formula:
    - When confirmed visitors exist:
      final = (0.6 * ML_predicted) + (0.4 * confirmed * 50)
    - Scale factor of 50: each confirmed user represents ~50 actual visitors.
    - Floor: blended count is always >= estimated real visitors.
    - When no confirmed visitors: ML prediction returned as-is.

  * API Endpoints:
    - POST /confirm-visit: Store a confirmed visit
    - POST /cancel-visit: Remove a confirmed visit
    - POST /live-stats: Get confirmed counts for a date

  * Frontend:
    - Green pulsing "Live Confirmed" indicator on crowd card.
    - "I'm Visiting" / "Cancel My Visit" toggle button.
    - Prediction source bar showing: ML count, confirmed count, adjusted total.
    - Automatic re-prediction after confirming/cancelling.
